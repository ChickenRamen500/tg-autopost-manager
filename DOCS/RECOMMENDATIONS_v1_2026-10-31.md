# Рекомендации по улучшению проекта (tg-autopost-manager)

**Дата:** 31.10.2026
**Статус:** черновик для обсуждения / разбивки на задачи
**Приоритеты:** `P0` — критично (баги/безопасность), `P1` — важно (архитектура), `P2` — желательно (производительность/инфраструктура).

## 1. Критические баги (P0)

### 1.1. Throttle уведомлений блокируется при коротком аптайме (`notifications.py`)

**Проблема.** В `notify_queue_almost_empty()` используется:

```python
now = time.monotonic()
last = _last_almost_empty.get(queue_id, 0.0)   # дефолт 0.0
if now - last < _NOTIFY_THROTTLE_SEC:
    return  # «уже отправляли недавно»
```

`time.monotonic()` отсчитывается от произвольной точки (обычно — загрузки ОС), но если процесс/система запущены недавно и monotonic clock мал (например, `< 300` секунд после boot в некоторых окружениях/на Windows uptime-счётчиках), выражение `now - 0.0 < 300` оказывается **истинным**, и первое (и все последующие до достижения аптайма в 5 минут) уведомление «Скоро закончится» **молча не отправляется**. Тот же антипаттерн дублируется в `archive.py`: `_last_archive_send_time` инициализируется как `0.0`, из-за чего первая отправка в архив вынужденно спит до `ARCHIVE_SEND_INTERVAL` секунд после старта.

**Решение.** Использовать `None` как маркер «ещё не отправляли»:

```python
_last_almost_empty: dict[int, float | None] = {}
...
last = _last_almost_empty.get(queue_id)
if last is not None and now - last < _NOTIFY_THROTTLE_SEC:
    return
_last_almost_empty[queue_id] = now
```

Аналогично в `archive.py`:

```python
_last_archive_send_time: float | None = None
...
if _last_archive_send_time is not None:
    elapsed = time.monotonic() - _last_archive_send_time
    if elapsed < ARCHIVE_SEND_INTERVAL:
        await asyncio.sleep(ARCHIVE_SEND_INTERVAL - elapsed)
```

Дополнительно: при пополнении очереди следует сбрасывать запись в `_last_finished`/`_last_almost_empty`, чтобы throttle не «съедал» следующее уведомление после возобновления постинга (проверить текущее поведение one-shot множества `_last_finished`).

**Проверка.** Юнит-тест с monkeypatch-ом `time.monotonic` (значения 10, 50, …): первое уведомление проходит независимо от значения часов; повторное в пределах 300 с — блокируется; после сброса очереди — снова проходит.

### 1.2. CI отсутствует — регрессии не ловятся автоматически (P0)

**Проблема.** В репозитории нет `.github/workflows/` (ни GitHub Actions, ни иной CI). Существующие тесты (`tests/unit`, `tests/integration`, скрипты `scripts/check_phase1.py`, `check_phase2.py`) выполняются только вручную, поэтому регрессии вроде п. 1.1 попадают в main.

**Решение.** Минимальный pipeline на каждое PR/push в main:

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt -r requirements-dev.txt
      - run: ruff check . && ruff format --check .
      - run: pytest tests/unit -q
      - run: python scripts/check_phase1.py && python scripts/check_phase2.py
```

Плюс **gate-check покрытия** (см. п. 3.4) — пайплайн должен падать, если покрытие ключевых модулей упало ниже порога.

**Проверка.** PR с заведомо падающим тестом не мержится; бейдж статуса CI в README.

## 2. Безопасность

### 2.1. Молчаливое отключение авторизации при пустом `SECRET_TOKEN` (P0)

**Проблема.** Единый секрет `SECRET_TOKEN` используется сразу в трёх местах, и во всех трёх при его отсутствии включается режим «auth отключён»:

- `app/api/routes/quick_add.py::_check_auth()` — `return` без проверки (REST API открыт);
- `app/web/deps.py` — веб-интерфейс полностью открыт;
- `app/main.py` (health-endpoints) — только warning в лог при старте.

Боевой деплой с забытым/пустым `SECRET_TOKEN` = **открытый API и админка**, причём единственная защита — предупреждение в логах, которое никто не читает.

**Решение.**
1. Fail-fast в production: при `ENV=production` (или отдельном флаге `ALLOW_OPEN_AUTH=false` по умолчанию) старт приложения должен **падать**, если `SECRET_TOKEN` пуст. Разрешать open-auth только явно (`ENV=development`).
2. Сохранить текущий UX для локальной разработки, но сделать его видимым: баннер `/` веб-интерфейса «⚠️ AUTH DISABLED», а не только строка в stdout.

**Проверка.** Тест: `settings.env == "production"` + пустой токен → `validate()` возвращает ошибку/исключение; dev + пустой токен → старт разрешён.

### 2.2. Разделение секретов по областям применения (P1)

**Проблема.** Один `SECRET_TOKEN` одновременно: (а) пароль HTTP Basic Auth для веба, (б) Bearer-секрет REST API для Chrome-расширения, (в) токен health-endpoints. Утечка из расширения (JS-код у пользователя) компрометирует и админку, и API.

**Решение.** Ввести отдельные переменные с обратной совместимостью:

| Переменная | Область | Fallback |
|---|---|---|
| `WEB_PASSWORD` | Basic Auth веб-интерфейса | `SECRET_TOKEN` |
| `API_TOKEN` | `/api/*` (quick_add, расширение) | `SECRET_TOKEN` |
| `HEALTH_TOKEN` | `/health/*` | `SECRET_TOKEN` |

Реализация — на уровне `settings` (поле + `_get("WEB_PASSWORD") or _get("SECRET_TOKEN")`), менять маршрутизацию не нужно. В `.env.example` пояснить миграцию.

### 2.3. Constant-time сравнение токенов — уже сделано, зафиксировать регрессионным тестом (P2)

Во всех трёх точках (`quick_add.py`, `web/deps.py`, `main.py`) уже используется `secrets.compare_digest` — это правильно. Рекомендация: добавить unit-тест, запрещающий появление новых compare-выражений вида `token == settings.secret_token` (grep-тест или simple AST-линтер в CI), чтобы правило не нарушалось в будущих PR.

## 3. Архитектура

### 3.1. Рефакторинг «God-модулей» (P1)

**Проблема.** `app/bot/handlers/menu.py` — 1567 строк (для сравнения: весь остальной `handlers/` ~1800). Файл смешивает навигацию, CRUD очередей, настройки, пиксельную логику callback'ов. `gelbooru.py` (822) и `admin.py` (513) также на грани.

**Решение.** Разбить `menu.py` на пакет подмодулей по доменам, сохранив единый роутер:

```
app/bot/handlers/menu/
├── __init__.py        # собирает Router из подмодулей (публичный API не меняется)
├── navigation.py      # главное меню, back-навигация
├── queues.py          # список/создание/редактирование очередей
├── settings_ui.py     # экраны настроек (threshold, archive channel, ...)
└── keyboards.py       # фабрики клавиатур этого домена
```

Критерий приёмки: ни один handler-модуль > ~400 строк; существующие тесты (`test_gelbooru_ui.py`, `test_keyboards.py`) проходят без изменений импортов верхнего уровня.

### 3.2. Dependency Injection вместо глобальных синглтонов (P1)

**Проблема.** Глобальные состояния: singleton `_db` в `app/db/database.py`, `_last_archive_send_time`/lock в `archive.py`, словари throttle в `notifications.py`, `get_bot()` через отложенный импорт внутри функций. Это мешает тестированию (нужны monkeypatch'и), запрещает несколько контекстов (worker/scheduler в одном процессе) и создаёт неявные циклы зависимостей (`notifications` → `bot.runtime` → `repositories`).

**Решение.** Поэтапно:
1. Ввести `AppContext` (dataclass: `db`, `bot`, `settings`, `clock`), создавать в `main.py` при startup, передавать в репозитории/сервисы явным аргументом (FastAPI Depends для API, `DataStore`/middleware для aiogram).
2. Заменить отложенные импорты `from app.bot.runtime import get_bot` внутри функций на инъекцию провайдера бота.
3. Часы/throttle-состояния вынести в инжектируемый объект `ThrottleState(now=time.monotonic)` — тесты перестанут патчить модульные dict'ы.

Не требуется внедрять фреймворк (dependency-injector и т.п.) — достаточно явных параметров и context-объекта.

### 3.3. Версионные миграции БД (P1)

**Проблема.** Миграции реализованы как жёстко закодированный Python-список `migrations = [...]` в `_run_migrations()` (`database.py`), схема применяется идемпотентным `schema.sql` при каждом старте. Нет номера версии, нельзя узнать состояние чужой БД, нельзя откатить, сложно добавлять миграции безопасно (порядок зависит от позиции в списке, условная логика per-migration отсутствует).

**Решение.** Перейти на `PRAGMA user_version`:
1. При старте читать `user_version`; каждый шаг миграции имеет целочисленный номер и выполняется только если `user_version < N`, после успеха ставит `user_version = N`.
2. Скрипты миграций хранить как пронумерованные файлы `app/db/migrations/0007_....sql` (или функции в реестре), а не inline-список.
3. `schema.sql` оставить как «свежую» схему для новых установок; для существующих БД путь — только миграции.
4. Добавить CLI `python scripts/db_version.py` (показать текущую версию) и тест «миграция с чистой БД == результат schema.sql» (сравнение `sqlite_master`).

### 3.4. Gate-check покрытия тестами (P1)

**Проблема.** Тесты есть (17 unit-файлов + интеграционные), но нет минимального порога покрытия; новые сервисы могут добавляться без тестов.

**Решение.** В CI: `pytest --cov=app --cov-report=term-missing` с `fail_under` (например, 70% общий, 90% для `app/services/**` и `app/repositories/**` через `coverage` config в `pyproject.toml`). Тесты для п. 1.1 и 2.1 добавить вместе с фиксами.

## 4. Производительность

### 4.1. Connection pool для SQLite вместо одного разделяемого соединения (P2)

**Проблема.** Вся архитектура держит **один** `aiosqlite.Connection` на процесс (`_db` singleton). Все запросы сериализуются через единственный поток aiosqlite; длинные SELECT (выборки gelbooru_seen_posts, дашборды веба) блокируют короткие записи планировщика, а `busy_timeout=5000` при параллельном доступе CLI-скриптов приводит к таймаутам под нагрузкой.

**Решение.** Не менять single-writer модель SQLite, но:
1. Пул из N read-only соединений (`PRAGMA query_only=ON`) для чтений репозиториев/веба + одно writer-соединение (WAL позволяет конкурентное чтение во время записи).
2. Простой пул на `asyncio.Queue[Connection]` (~50 строк) достаточен; ORM/SQLAlchemy не нужен.
3. Интерфейс `get_db()` сохранить, добавив `get_read_db()`.

### 4.2. Группировка записей в транзакции (P2)

**Проблема.** Репозитории вызывают `await db.commit()` на каждую операцию (см. commit-точки в `database.py` и репозиториях). Пакетная вставка альбома из 10 медиа или импорт подписки = 10 отдельных fsync'ов (даже при `synchronous=NORMAL` WAL делает группировку менее болезненной, но накладные расходы остаются).

**Решение.** Ввести контекстный менеджер `async with db.transaction():` (отключает autocommit-логику репозиториев) и обернуть батчи: `add_media_group`, массовые обновления статусов в scheduler, `_run_migrations` целиком. Проверка: профилировка `time insert_album(10 media)` до/после.

### 4.3. Недостающие индексы (P2)

В `schema.sql` 10+ индексов, но стоит проверить профилированием (`EXPLAIN QUERY PLAN`) следующие типовые фильтры:

- `posts(status, scheduled_at)` — планировщик выбирает pending-посты по времени; сейчас используется только составной `(queue_id, status)`;
- `queues(is_active)` / `channels(is_active)` — если такие фильтры есть в выборках;
- частичный индекс `posts(file_unique_id) WHERE file_unique_id IS NOT NULL` (сейчас `idx_posts_file_unique` включает NULL-строки);
- `task_queue(status, created_at)` — воркер выбирает задачи в порядке очереди.

Перед добавлением — снять реальные планы запросов; после — тест на `PRAGMA integrity_check` + сравнение планов в CI-скрипте.

## 5. Инфраструктура

### 5.1. Вынос runtime-данных из Docker-образа (P2)

**Проблема.** `.dockerignore` уже исключает `data/*.db*` и медиа, но сам каталог `data/` копируется в образ ради `.gitkeep`, а `docker-compose.yml` монтирует `./data:/app/data` поверх. Любое изменение структуры `data/` требует пересборки образа; на Windows залоченные контейнером файлы периодически ломают сборку (что и описано в комментариях `.dockerignore`).

**Решение.** Полностью убрать `data/` из build context: структуру каталогов создавать кодом при старте (`init_db()` уже делает `mkdir(parents=True, exist_ok=True)` — расширить на downloads/media). В compose заменить bind-mount на именованный volume либо оставить bind, но без копирования скелета в образ. Обновить `QUICKSTART_NEW_MACHINE.md`.

### 5.2. Пиннинг зависимостей (P2)

**Проблема.** `requirements.txt` использует диапазоны (`fastapi>=0.100,<1.0`, `yt-dlp>=2024.0`). `yt-dlp` особенно опасен: он обновляется еженедельно и регулярно ломает парсинг сайтов — сборка «на прошлой неделе» и «сегодня» даёт разное поведение. Воспроизводимость docker-сборок отсутствует.

**Решение.** Добавить `requirements.lock` (через `pip freeze` или `uv pip compile` / `pip-tools`) и собирать образ из него; `requirements.txt` оставить как источник прямых зависимостей. Для `yt-dlp` — жёсткий пин + отдельная задача «обновить yt-dlp» с прогоном интеграционных тестов парсеров перед bump'ом.

### 5.3. Актуализация документации (P2)

**Проблема.** В `DOCS/` лежат PHASE1/PHASE2 гайды, структура проекта и ТЗ v5, но: описание auth-модели расходится с реальностью (open-auth при пустом токене — см. п. 2.1), нет страницы об architecture decision records (ADR), нет runbook'а восстановления БД; `README.md` не упоминает health-endpoints и их защиту.

**Решение.**
1. После реализации п. 2.1–2.2 обновить раздел auth в `PROJECT_STRUCTURE.md` и `.env.example` (таблица «переменная → область»).
2. Завести каталог `DOCS/adr/` с короткими ADR (формат: контекст / решение / следствия) — первые: «SQLite + WAL без ORM», «aiogram 3 + FastAPI в одном процессе», «single SECRET_TOKEN → разделённые секреты».
3. Runbook: резервное копирование `bot.db`/`tags.db` (`VACUUM INTO`), восстановление, миграция версий схемы (п. 3.3).
4. Правило в CONTRIBUTING/CI: изменён публичный API или env-переменные → PR обязан содержать diff документации.
