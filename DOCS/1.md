## Часть A. Подготовка (один раз)

### A1. Установите Docker Desktop
Проверка:
```powershell
docker --version
docker compose version
```

### A2. Получите api_id / api_hash (для Local Bot API Server)
1. Зайдите на **https://my.telegram.org** под своим аккаунтом Telegram;
2. Раздел **«API development tools»** → создайте приложение → скопируйте `api_id` (число) и `api_hash` (строка).
   ⚠️ Если форма отвечает голым `ERROR` — см. `DOCS/my_telegram_org_troubleshooting.md`
   (IP должен быть из страны аккаунта, App title — UpperCamelCase без дефисов).

### A3. Создайте бота и возьмите токен
1. Напишите **@BotFather** → `/newbot` → скопируйте `BOT_TOKEN` (вид: `123456:AA...`).

### A4. Узнайте свой tg_id
Напишите **@userinfobot** — он ответит числом. Это ваш `tg_id` → впишете в `.env` как `ADMIN_TG_ID`.

### A5. Заполните `.env`
```powershell
Copy-Item .env.example .env     # Linux/macOS: cp .env.example .env
```
Откройте `.env` в редакторе и заполните **минимум** эти поля:

| Поле | Что вписать | Пример |
|---|---|---|
| `BOT_TOKEN` | токен от @BotFather | `123456:AAH...` |
| `TELEGRAM_API_ID` | из my.telegram.org | `12345678` |
| `TELEGRAM_API_HASH` | из my.telegram.org | `0123abc...` |
| `SECRET_TOKEN` | любая длинная случайная строка (пригодится в Фазе 4) | `openssl rand -hex 32` |
| `ADMIN_TG_ID` | ваш tg_id из @userinfobot | `987654321` |
| `TEST_CHAT_ID` | ваш chat id для теста 300 МБ (Фаза 1) | тот же tg_id |

⚠️ В `docker-compose.yml` есть volume `D:\Media:/app/media`. Если у вас диск не `D:` —
поправьте путь в `docker-compose.yml`, иначе `docker compose up` упадёт с ошибкой монтирования.

## Часть B. Полная перезагрузка «с нуля»

Удаляет контейнеры, образы, volumes (включая кеш local-bot-api) и локальную БД.
**Все очереди/посты/пользователи из старой БД будут потеряны.**

```powershell
# 1. Остановить и удалить контейнеры + named volumes + образы проекта
docker compose down -v --rmi local

# 2. Удалить локальные данные (БД, media, downloads)
Remove-Item data\bot.db*, data\media\*, data\downloads\* -ErrorAction SilentlyContinue
# Linux/macOS: rm -f data/bot.db* && rm -rf data/media/* data/downloads/*

# 3. Пересобрать образ бота без кеша
docker compose build --no-cache

# 4. Поднять все контейнеры
docker compose up -d

# 5. Подождать 10–30 секунд и посмотреть статус
docker compose ps
```

Ожидаемый результат `docker compose ps`:

| Сервис | Status | Ports |
|---|---|---|
| `tg-lba` (local-bot-api) | Up (healthcheck может быть «starting» до ~90 сек при первой синхронизации с датацентром Telegram) | 8081 |
| `run-...-bot-1` | Up | 8000 |

При первом старте `lifespan` приложения сам создаст `data/bot.db` со всеми 9 таблицами
и сделает пользователя из `ADMIN_TG_ID` админом. Дополнительно можно явно:
```powershell
docker compose exec bot python scripts/init_db.py
```

## Часть C. Обычный ежедневный запуск

Ничего удалять не нужно:
```powershell
docker compose up -d          # поднять (если погашены)
docker compose logs -f bot    # смотреть логи (Ctrl+C — выйти, контейнер останется работать)
docker compose restart bot    # перезапустить бота (например, после смены кода/конфига)
docker compose down           # остановить (данные и volumes сохраняются)
```

После изменения кода на хосте (без пересборки образа, если код примонтирован — нет,
в текущем Dockerfile код копируется в образ, поэтому):
```powershell
docker compose up -d --build bot
```

## Часть D. Проверка, что всё работает

### D1. Health-эндпоинты (самый быстрый способ)

```powershell
curl http://localhost:8000/health
```
Хороший ответ:
```json
{"status":"ok","phase":2,"bot_api_url":"http://local-bot-api:8081","config_problems":[]}
```
⚠️ Если в `config_problems` что-то перечислено — это отсутствующие поля `.env` (см. Часть A5).

```powershell
curl http://localhost:8000/health/bot-api
```
Хороший ответ (означает: Local Bot API жив, logOut выполнен, токен принимается):
```json
{"status":"ok","bot":{"username":"your_bot","id":123456}}
```
Если `status:error` → см. диагностику ниже (логичнее всего — не сделан `logOut`, п. D3).

```powershell
curl http://localhost:8000/health/scheduler
```
Хороший ответ (job'ы появляются только если есть активные очереди, см. Часть E):
```json
{"status":"ok","jobs":[{"id":"queue_1","next_run":"2026-10-12 ..."}]}
```

### D2. Проверка схемы БД и RBAC (ТЗ §5, §2.6)
```powershell
docker compose exec bot python scripts/check_phase2.py --db
```
Ожидается:
```
[OK] Все 9 таблиц из ТЗ §5 присутствуют: channels, duplicate_hashes, posts, queues,
     routing_rules, signatures, tag_subscriptions, task_queue, users
[OK] RBAC: admin >= moderator, moderator не проходит admin-проверку
[OK] admin в БД: tg_id=... role=admin
```
(Предупреждение `[!] ADMIN_TG_ID не задан` появляется, если вы не заполнили `ADMIN_TG_ID`.)

### D3. Проверка миграции с облачного API (Фаза 1, разовая процедура)
```powershell
docker compose exec bot python scripts/check_phase1.py --logout   # сделать logOut (безопасно повторять)
docker compose exec bot python scripts/check_phase1.py --health   # getMe через localhost:8081 → [OK]
```
Без `logOut` локальный сервер возвращает 401/409 — самый частый источник `status:error` в D1.

### D4. Маршрутизация (ТЗ §2.2.2)
```powershell
docker compose exec bot python scripts/check_phase2.py --routing
```
Ожидается:
```
[OK] Точное совпадение telegram_channel/@anime_channel → queue 1
[OK] Regex по тегам gelbooru (.*rating:safe.*) → queue 1
[OK] Нет правила для x.com → Входящие (None)
```
⚠️ Скрипт создаёт демо-канал/очередь/правила в той же БД `data/bot.db` — для чистовой
проверки запускайте его до реальной настройки или на копии БД.

### D5. Планировщик
```powershell
docker compose exec bot python scripts/check_phase2.py --scheduler
```
Пока очередей нет — `job'ов: 0` это нормально. После `/add_queue` + рестарта бота
(`docker compose restart bot`) появится `queue_<id>` c `next_run`.

### D6. (Опционально, Фаза 1) Тест большого файла 300 МБ через Local Bot API
```powershell
docker compose exec bot python scripts/check_phase1.py --big-test
```
Требует заполненный `TEST_CHAT_ID`. Проходит = лимиты 50/20 МБ сняты (upload до 2 ГБ).

### D7. Юнит-тесты и линтер (на хосте или в контейнере)
```powershell
pip install -r requirements.txt
python -m pytest tests/unit -q        # ожидается: 22 passed
python -m ruff check app/ scripts/ tests/ conftest.py   # All checks passed!
```
⚠️ Если на хосте стоит «грязное» окружение с чужими pytest-плагинами (например, libtmux),
запускайте так:
```powershell
$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD=1; python -m pytest tests/unit -q
```

## Часть E. Функциональная проверка Фазы 2 через Telegram

Всё предыдущее проверяло инфраструктуру. Теперь — сквозной сценарий руками:

1. **Найдите бота в Telegram, напишите `/start`** (с того же аккаунта, чей tg_id в `ADMIN_TG_ID`)
   → бот ответит приветствием, а middleware автоматически сделает вас **admin**.
2. **Добавьте канал** (бот должен быть админом в этом канале!):
   ```
   /add_channel -100XXXXXXXXXX MyChannel @my_channel
   ```
   `tg_chat_id` канала вида `-100…` — узнать: перешлите пост из канала боту либо используйте @getidsbot.
3. **Создайте очередь** (channel_id — id из таблицы `channels`, обычно 1):
   ```
   /add_queue 1 "Anime Safe" 120
   ```
4. **Перезапустите бота**, чтобы планировщик зарегистрировал job новой очереди:
   ```powershell
   docker compose restart bot
   curl http://localhost:8000/health/scheduler
   ```
   → должен появиться `queue_1` с `next_run` через ~2 часа.
5. **Пришлите боту фото/видео/GIF/документ в ЛС** (или перешлите пост из канала).
   Ожидаемая реакция:
   - обычное фото из ЛС → `📥 Пост #N добавлен во «Входящие»` (нет правила маршрутизации);
   - форвард из канала, для которого создано правило → `✓ Пост #N добавлен в очередь «Anime Safe»`;
   - повторно прислать **тот же файл** → `⚠️ Похоже на дубликат … possible_duplicate` (дедуп по file_unique_id).
6. Проверьте списки:
   ```
   /list_queues
   /queue 1
   /stats
   ```
7. **Тест публикации по расписанию**: создайте очередь с интервалом 1 минута
   (`/add_queue 1 "Test Q" 1`), добавьте туда пост, `docker compose restart bot` —
   через минуту пост должен появиться в канале. Статус в `/queue` сменится на `sent`.
   (Отправка идёт по `tg_file_id` — файл не скачивается и не грузится заново, ТЗ §2.5.1.)

## Быстрая диагностика: что делать, если не работает

| Симптом | Причина → решение |
|---|---|
| `docker compose up` падает на volume | Пути `D:\Media` нет / Docker Desktop не расшарил диск → Settings → Resources → File Sharing, или поправьте путь в compose |
| `/health/bot-api` → `error`, в логах 401/409 | Не сделан `logOut` с облачного API → `docker compose exec bot python scripts/check_phase1.py --logout` |
| `tg-lba` вечно `starting` | Первая синхронизация с DC Telegram (до 90 сек) — ждите; дольше — `docker logs tg-lba` (часто неверные api_id/api_hash) |
| Бот молчит в ЛС | `BOT_TOKEN` неверен, или polling упал → `docker compose logs bot | grep -i polling`; проверьте `/health` на `config_problems` |
| Гость пишет боту → «🔒 Доступ закрыт» | Так и задумано (RBAC, ТЗ §2.6): добавьте через `/add_user` от админа |
| `/add_user` не работает | Вы не admin: проверьте `ADMIN_TG_ID` в `.env`, затем `/start` |
| Новая очередь не публикует | Планировщик читает очереди на старте → `docker compose restart bot` |
| `pytest` на хосте падает плагином libtmux | `$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` перед запуском (в контейнере этого нет) |
| Логи непонятные | `docker compose logs -f bot local-bot-api` — читайте сверху вниз, ошибки помечены ERROR/exception |
