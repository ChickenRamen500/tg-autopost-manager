## Часть 2 — Новый баг с твоего production: `TelegramRetryAfter` на `message.answer`

### Твой лог
```
TelegramRetryAfter: Telegram server says - Flood control exceeded on method 'SendMessage' in chat 670635487. Retry in 5 seconds.
File "/app/app/bot/handlers/media.py", line 298, in receive_media
    await message.answer(
```

### Что происходит

Когда ты пересылаешь боту много медиа за короткое время (или отправляешь серию альбомов), **каждый forwarded media триггерит `receive_media`**, который:

1. `media.py:260-267` — `archive_post()` шлёт пост в служебный канал (`bot.send_photo`/`send_video`/`send_document`)
2. `media.py:282` или `:291` или `:298` — `message.answer(...)` — ответ-подтверждение тебе в ЛС

Дополнительно (после PR #31, в Фазе 2), если в момент пересылки срабатывает scheduler и отправляет пост → `notify_admin()` / `notify_queue_almost_empty` / `notify_queue_finished` / `notify_send_error` — все шлют в `settings.admin_tg_id` (твой ЛС, chat_id 670635487).

**Все эти `SendMessage`-вызовы бьют в один chat (твой ЛС, `670635487` — положительное число, значит это user_id, а не -100 канал).** Лимиты Telegram: ~30 сообщений в секунду в один чат для ботов, но если ты шлёшь сериями по 5-7 в секунду — Telegram включает flood control с `retry_after=5`.

### Где проблема в коде

`app/bot/handlers/media.py:298`:
```python
await message.answer(
    f"✓ Пост #{post_id} → очередь «{qname}» (позиция ~{pending_count})",
    reply_to_message_id=message.message_id,
)
```

`message.answer` — это `bot.send_message(chat_id=message.chat.id, text=...)`. Если он бросает `TelegramRetryAfter`, **исключение не ловится** — оно поднимается до aiogram dispatcher, который логирует «Cause exception while process update» и помечает апдейт как «not handled».

### Важные нюансы

1. **Пост уже сохранён в БД** к моменту ошибки: `posts_repo.create_post()` (строка 296, до `message.answer` на строке 298) уже выполнен. То есть ты не теряешь посты — ты теряешь только подтверждение.

2. **Архивация тоже может упасть** — `archive_post` (строка 265) обёрнут в `try/except Exception` (строки 260-267) — он молча логируется как warning. Но если `archive_post` слал в служебный канал и получил `RetryAfter`, пост уже не будет заархивирован (нет retry).

3. **`notifications.py` тоже не retry'ит** — `notify_admin` (строка 32) оборачивает в `try/except Exception`, но НЕ ловит `TelegramRetryAfter` отдельно → нет `await asyncio.sleep(retry_after)` + retry. Просто «не удалось отправить» в лог.

4. **Это та же корневая бага, что я флаговал в первоначальном ревью как #7** — там речь шла про scheduler's `send_photo`/`send_video`/`send_media_group`, тут — про handler's `message.answer`. **Разные кодовые пути, один корень: `TelegramRetryAfter` нигде не ловится отдельно.**

### Что нужно сделать (минимум)

```python
# В media.py вокруг message.answer
from aiogram.exceptions import TelegramRetryAfter

async def _safe_answer(message, text, **kwargs):
    try:
        await message.answer(text, **kwargs)
    except TelegramRetryAfter as e:
        logger.warning("Flood control: ждём %s сек, retry", e.retry_after)
        await asyncio.sleep(float(e.retry_after) + 0.5)
        try:
            await message.answer(text, **kwargs)
        except Exception:
            logger.warning("Retry ответа тоже упал — пропускаем")
    except Exception as e:
        logger.warning("Не удалось отправить ответ: %s", e)
```

И обернуть все ~5 вызовов `message.answer` в `receive_media`.

### Что нужно сделать (правильно, для системы в целом)

Ввести **per-chat rate limiter** для всех `bot.send_*`/`message.answer`/`call.answer`/`notify_*`:

```python
# app/services/rate_limiter.py (новый)
import asyncio
from collections import defaultdict

class ChatRateLimiter:
    """Лимит SendMessage на чат: не более N за T секунд, иначе ждём."""
    def __init__(self, max_per_window: int = 25, window_sec: float = 1.0):
        self._max = max_per_window
        self._window = window_sec
        self._timestamps: dict[int, list[float]] = defaultdict(list)
        self._lock = asyncio.Lock()

    async def acquire(self, chat_id: int) -> None:
        async with self._lock:
            now = asyncio.get_event_loop().time()
            ts = self._timestamps[chat_id]
            # Чистим старые
            self._timestamps[chat_id] = [t for t in ts if now - t < self._window]
            if len(self._timestamps[chat_id]) >= self._max:
                wait = self._window - (now - self._timestamps[chat_id][0])
                if wait > 0:
                    await asyncio.sleep(wait)
            self._timestamps[chat_id].append(asyncio.get_event_loop().time())

chat_limiter = ChatRateLimiter(max_per_window=25, window_sec=1.0)
```

Применять перед каждым `bot.send_*(chat_id=...)`, `message.answer()` (через промежуточный helper), `notify_admin`. Это убирает flood control целиком.

**Альтернатива для `receive_media` (UX-friendly)**: при получении серии медиа за короткое окно — группировать подтверждения в одно сообщение «✓ Получено N постов: #1, #2, #3 → очередь «X»». Тот же debounce-паттерн, что для альбомной архивации в `media.py:_schedule_album_archive`.

## Часть 3 — Регрессии, введённые фиксами

### 🔴 Regression #1 — HTML-инъекция (CRITICAL, из PR #32)

PR #32 выставил `parse_mode=ParseMode.HTML` глобально (`local_bot_api.py:55-59`), но **ни одной `html.escape()` не добавлено**. Греп подтверждает: 0 совпадений `html.escape`, `import html`, `from html import` по всему репозиторию.

**Это та самая регрессия, которую предыдущий ревьюер ЯВНО предупреждал** в worklog.md (кросс-каттинги #2 и #5):
> "Adding parse_mode=\"HTML\" later WITHOUT escaping user-controlled text (captions, usernames, channel names) in f-string builders would create HTML injection — latent risk. When fixing parse_mode issue, ALSO add html.escape(...) calls or switch to MarkdownV2 with proper escaping."

PR #32 это предупреждение проигнорировал.

**28+ f-строк с пользовательским текстом** теперь интерполируются в HTML-parsed message bodies без эскейпинга. Самые опасные:

| Что | Где | Источник |
|---|---|---|
| `post['original_caption']` | `menu.py:419` (`_render_post_card`) | Любой пересланный caption — полностью атакер-контролируемый |
| `q['name']`, `c['name']` | `menu.py:181, 396, 478, 547, 558, 613, 757, 886, 894`; `admin.py:47, 282, 294, 306, 425` | Admin-supplied (через FSM или `/add_*`) |
| `user['username']` | `menu.py:1204`; `admin.py:249` | Telegram-supplied, мутабельный |
| `rule['source_pattern']` | `menu.py:1042, 1081` | Admin-supplied (regex) |
| `q.get('channel_username')`, `existing['username']` | `admin.py:47, 282, 306` | Admin/Telegram-supplied |
| `post.get('source_id', '?')` | `menu.py:339-340` | Callback data из пересланного поста |

**Эксплойты**:
1. **Любой юзер** пересылает боту фото с caption `<a href="t.me/evilbot">Join premium</a>` → пост сохраняется с этим `original_caption` → админ открывает пост в inbox → `_render_post_card` (`menu.py:419`) интерполирует caption напрямую в HTML → **админ видит кликабельную phishing-ссылку**.
2. **Админ** называет канал `<a href="https://evil.tld/phish">Support</a>` → каждый channel-list rendering (`admin.py:306`, `menu.py:478`) показывает кликабельную «Support» ссылку → moderator кликает → фишинг.
3. **Админ** называет очередь `<b>test</b>` → queue card рендерит «test» жирным везде.
4. **Юзер с username** `<a href="evil">x</a>` → user-list rendering инъецирует ссылку.

**Фикс**: добавить `import html` в начале каждого файла + обернуть каждую интерполяцию пользовательского текста в `html.escape(...)`. ~28 сайтов, по 1 строке на каждый.

### 🟠 Regression #2 — `posts.queue_id ON DELETE CASCADE` вместо SET NULL (HIGH, из PR #31)

`app/db/schema.sql:89` теперь:
```sql
FOREIGN KEY (queue_id) REFERENCES queues(id) ON DELETE CASCADE
```

ТЗ §2.3.4 требовало `ON DELETE SET NULL` — посты должны **возвращаться в inbox** при удалении очереди (это прямо упоминалось в комментах schema.sql:63 `NULL = «Входящие» (inbox)`). PR #31 сделал CASCADE → **посты удаляются outrightly**. Админ, удаляющий очередь, **молча теряет посты**.

Усугубляется отсутствием миграции: SQLite не может ALTER FK на существующих таблицах (`_run_migrations` в `database.py:86-126` делает только `ALTER TABLE ADD COLUMN`). Текущий эффект:
- Существующие БД (созданные до PR #31): FK остаётся RESTRICT → `remove_queue` всё ещё бросает `IntegrityError` (теперь ловится `try/except`, но удалять всё равно нельзя).
- Свежие БД (после PR #31): CASCADE → посты тихо удаляются.
- **Три разных поведения в зависимости от возраста БД.**

**Фикс**: поменять CASCADE → SET NULL в schema.sql + написать миграцию: `CREATE TABLE _posts_new ... INSERT SELECT ... DROP TABLE posts ... ALTER TABLE _posts_new RENAME TO posts ...` + recreate indexes.

### 🟡 Regression #5 — `notifications._last_notify` общий dict глушит «finished» (MEDIUM, из PR #33)

`app/services/notifications.py:52` — `_last_notify: dict[int, float]` keyed только по `queue_id`. И `notify_queue_almost_empty` (L66-68), и `notify_queue_finished` (L85-87) используют **один и тот же dict**.

Сценарий:
1. Очередь падает до 3 постов → `notify_queue_almost_empty` fires, `_last_notify[qid] = t1`
2. В течение 5 минут очередь доходит до 0 → `notify_queue_finished` проверяет `now2 - t1 < 300` → True → **return early** → админ **никогда не видит «очередь закончилась»**

PR #33 пытался сделать `notify_queue_finished` one-shot через комментарий «отправляем только ОДИН раз», но реализация не одна-shot — через 5 минут оно может пере-fire'нуть.

**Фикс**: разнести на `_last_almost_empty` и `_last_finished` (или композитные ключи `(queue_id, kind)`), + хранить «previous pending count» чтобы fire «finished» только на переходе non-zero → zero.

### 🟡 Regression #6 — cache cleanup task cancel не awaited (MEDIUM, из PR #31)

`app/main.py:130-131`:
```python
if _cache_cleanup_task and not _cache_cleanup_task.done():
    _cache_cleanup_task.cancel()
```

Сравни с `_bot_polling_task` который правильно awaited (`main.py:117-121`):
```python
_bot_polling_task.cancel()
try:
    await _bot_polling_task
except asyncio.CancelledError:
    pass
```

`cache._cleanup_task` только `.cancel()` без `await`. `cache.cleanup_loop` ловит `except Exception`, но `CancelledError` — `BaseException` в Py 3.8+ → не ловится → поднимается как task's exception → asyncio логирует «Task exception was never retrieved» при GC. Race: процесс может выйти до того, как задача увидит отмену.

**Фикс**: добавить `try: await _cache_cleanup_task except asyncio.CancelledError: pass` после `.cancel()`.
